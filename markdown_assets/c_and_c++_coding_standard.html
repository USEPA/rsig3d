1. Purpose

The purpose of this coding standard is to help communicate expectations of and techniques to achieve consistent high-quality of coding artifacts across the project(s) and its developers. Consistency (of both form and semantic models) enhances understandability, ease of use, testability, extendibility, reusability and compatibility.

This document is a start but should not be considered a complete definition of all of the expectations of coding style.

This document defines references to baseline source documents upon which this standard is based - the "required and recommended reading" of developers on these projects. It also lists the guidelines that developers are expected to adhere to and review each others code against. Guidelines are "musts" unless they are worded otherwise (e.g., "prefer"). Finally, exemplars are provided for each coding artifact and reviewed code will be compared against them. The Quality Assurance Lead will have final authority on disputes with this standard and proposals to change it.

4. Guidelines

McConnell's Software Development Checklists contain useful items to incorportate.

Ellemtel C++ Coding Standard is a good starting point C++ standard. The following guidelines include some exceptions to Ellemtel.

1. Use .C and .h for C++ source files.

2. Avoid #include "Foo.h" and instead use #include <Foo.h> and -I. (last) to detect name clashes at the point they are introduced (so they can be corrected). Header and library search paths (-I and -L) are ordered from most standard to least standard. For example, -L/usr/lib -L/usr/lib/X11 -L../external/lib/$arch -L../lib/$arch -L.

Ok to use #include "File.h" // For non-public headers in the current directory.

3. Always #include the header that defines the entity used. Don't rely on it being #included by other headers.

4. Don't #include headers that are not used. If they are conditionally used, #include them conditionally.

  #ifdef TIMING_TESTS
  #include <Timer.h> /* TimerGetElapsedSec(). */
  #endif

5. Always document why a header is being #included. E.g.,

  #include <iodecl3.h> /* For IOAPI_Bdesc3, IOAPI_Cdesc3, NAMLEN3. */

This facilitates removal of obsolete #includes (if its documented entities are no longer referenced in the file).

6. (For libraries at least) use Design By Contract implemented using the Assertions.h macros. Write detailed contracts. For example, in POST(), define the value of each output argument both upon success and failure of the routine. For example:

  POST( IMPLIES_ELSE( ok,
                      AND2( fileSelector->hostName[ 0 ],
                            fileSelector->userID[ 0 ] ),
                      IS_ZERO2( fileSelector->hostName[ 0 ],
                                fileSelector->userID[ 0 ] ) ) );

Also, make PRE() the first executable statement of the routine and POST() the last:

void fileReadString( File* file, char s[], Integer n ) {
  PRE3( fileIsReadable( file ), s, n > 0 );
  ...
  POST2( isReadMode( file ), strlen( s ) <= n );
}

Note all these assertion macros require semi-colons except DEBUG() and CHECKING() (since they can enclose arbitrary segments of code).

7. Use BasicNumerics.h for integer and real basic data types (at least for public interfaces):

#include <BasicNumerics.h> /* For Integer, Real. */

This facilitates efficient (non-copying), lossless, cross-language, cross-platform data sharing. Integer and Real are defined as (exactly) 64-bit types compatible with FORTRAN INTEGER(KIND=8) and REAL(KIND=8), respectively (and Java long and double). Read the NumericTypes.h header and read the source code of NumericTypesTest.c and the File Library (File.c) to learn how to use these types and their routines. Be careful to check ranges before passing (truncating) integers to external routines that expect int, long, size_t, etc. - see the File Library for examples of this.

For this project, it is OK to use various built-in types appropriately. Note: double and long long are 64-bits on all platforms.

8. In C, implement Failure-handling using the Failure Library which supports a global failure() routine, optional console-logging of messages (on by default), an optional callback and a global failure count.

In C++ use the standard std::exception classes and throw-catch logic but do not use throw specifications on routines (they are problematic and deprecated).

9. In C, use the Memory Library for dynamic memory allocation and deallocation. This provides macros that are convenient and defect trapping as well as a single point for memory management to facilitate instrumented debugging, testing and extendibility (e.g., to shared memory). Avoid using malloc(), free(), realloc(), calloc(), strdup(), etc.

In C++ use operator new.

10. Use the Stream Library for ASCII and binary data I/O. It provides convenient robust efficient and portable functionality. (See exemplar.)

11. Familiarize yourself with the other existing libraries used on the project. Read their documentation files (docs/*.txt), ask their authors if you have questions or suggested improvements and reuse them in code you develop.

    17. In declarations, try to separate the type from the variable name. In particular, declare pointers:

    not:

     int *count, *second;

    but:

     int* count  = 0;
 int* second = 0;

    For complicated types, use typedefs

    typedef void (*FailureHandler)( Integer failureNumber, const char* message );
extern void failureSetHandler( FailureHandler newFailureHandler );

    18. Write well-structured (single-entry-single-exit) loops and routines:

    • Don't use return in procedures (void routines).
    • Don't use multiple returns in functions.
    • Place return result; alone on a line after POST() and before the closing brace.
    • Don't use break, continue or goto.

    Well-structured form generally yields better testability (simpler graphs, applicable theory), understandability (tracing control/data flows) and extendibility (inserting new code into a routine).

    19. Don't use () around the result of return statements and sizeof operator's operands:

      return result; /* Not return(some-expression); */
  sizeof myList  /* Not sizeof(myList) */

    They are not functions so they should not appear as such.

    20. Prefer pre-increment to post-increment where the effect is semantically equivalent. (It reads better "increment value" (verb noun) vs "value increment" (noun verb) and is more efficient, especially for arbitrary types in C++, since it avoids copying to a temporary.)

     post-increment is:                            pre-increment is:
   const BigNumber copy( value );                /* No copy. */
   value = value + 1;                            value = value + 1;
   return copy;                                  return value;

    21. In routines with output arguments, make them last (after input arguments). Declare in/out arguments after inputs and before outputs. Exceptions to this are for routines intended to be compatible with other routines (e.g., standard library, strcpy) or that have self/this as the first argument. Note: an input argument is defined as one whose value is read by the routine and an output argument is one that is written.

    22. To the extent possible, declare variables nearest their first use. Consider using extra {} to achieve this. This minimization of "locality of reference" facilitates understandability (by chunking), data-flow analysis (both by human readers and optimizing compilers) and testing (often allowing for const declarations which might not otherwise be possible). For example:

      if ( foo ) {
    const char* const firstName = foo->names[ index ][ 0 ];
    ... /* firstName is unchangable and scope limited to this block */
  }

    23. Initialize variables during declaration (especially pointers).

      Foo* foo = 0; /* Avoid pointers to garbage. */

    Note: even reading an uninitialized value results in undefined behavior:

      Foo* p;
  ...many lines later...
  if ( a && b || c && p ) /* May crash if p wasn't initialized! */

    24. Prefer switch-case statements to long chains of if-then-else if...-else-end. (Switch is more efficient and often more readable.)

    25. Prefer table-driven approaches to switch-case statements. (More easily extendible - just add a table entry and the handler vs modify existing code.) Here's an example:

    static int parseCommandLineOptions( int argc, const char* argv[],
                                    UserParms* p ) {
  /* Table-driven option handling: */

  typedef int (*OptionHandler)( int, const char**, int*, UserParms* );

  typedef struct { const char* option; OptionHandler handler;} OptionTableEntry;

  static const OptionTableEntry optionsTable[] = {
    { "-site",            readSiteOption           },
    { "-grid",            readGridOption           },
    { "-output",          readOutputOption         },
    { "-gridvar",         readGridVarOption        },
    { "-sitevar",         readSiteVarOption        },
    { "-sitevarlat",      readSiteVarLatOption     },
    { "-sitevarlon",      readSiteVarLonOption     },
    { "-sitevarstat",     readSiteVarStatOption    },
    { "-siteregion",      readSiteRegionOption     },
    { "-sitetstep",       readSiteTstepOption      },
    { "-tsteppick",       readTstepPickOption      },
    { "-gridsamplesize",  readGridSampleSizeOption },
    { "-gridellipse",     readGridEllipseOption    },
    { 0, 0 }
  };

  int ok = 1, arg = 0;

  PRE3( argc >= 1, argv, p );

  for ( arg = 1; AND2( ok, arg < argc ); ) {
    const char* const opt = argv[ arg ];
    int option = -1;
    int index;

    for ( index = 0; AND2( option == -1, optionsTable[ index ].option );
          ++index ) {

      if ( strcmp( opt, optionsTable[ index ].option ) == 0 ) {
        option = index;
      }
    }

    if ( option != -1 ) {
      ok = optionsTable[ option ].handler( argc, (const char**) argv, &arg, p );
    } else {
      failure( "Invalid command-line option '%s'.", opt );
      ok = 0;
    }
  }

  ok = AND2( ok, finalUserParmsChecks( p ) );
  POST( IMPLIES( ok, isValidUserParms( p ) ) );
  return ok;
}

    29. Macros, if used, must be safe:

    1. ALL_CAPS - to warn the user that it is not a function.
    2. Where possible, in the definition:
      1. Use parenthesis around each argument.
      2. Use parenthesis around the entire macro.
      3. Make sure the macro is a single statement. Use 'do { statement1; statement2; ... } while ( 0 )' or the comma operator to wrap multiple statements.
    3. Don't pass arguments with side-effects to macros. (This includes function calls.)
    4. Don't use comments inside of macros. (It leads to unexpected surprises when macro calls are commented out.) 
          #define IS_VALID_GRID_DATA_TYPE(type) ((type) >= 0 && (type) < GRID_DATA_TYPES)

    31. In C, "Boolean" functions should be declared to return exactly Integer 1 or 0:

    RETURNS: Integer 1 if successful, else 0.

    RETURNS: 0 = failure; otherwise success

    38. In C, use an object-based approach for components. That is, define a structure for the ADT (but keeps its data definition private) and define the set of commands and queries for operating on it. These routines may either be global, in which their names must be prefixed with the name of the ADT type (example 1) or they may be embedded in the structure (example 2) in which case they can be concise since there is no global namespace clashes.

    Example 1, global function form:

#define fileClose(f) (fileClose_(f), (void)((f) = 0))

/* Except for the implementation, File is just an opaque structure: */

typedef struct File_ File;

/*================================ FUNCTIONS ================================*/

/* Constructors: */

extern File* fileOpen( const char* fileName, const char* mode );
...
/* Destructor: */

extern void fileClose_( File* file ); /* Used via fileClose() macro. */

/* Queries: */

extern Integer     fileIsValid(    const File* file ); /* Invariant. */
extern Integer     fileIsReadable( const File* file );
...
extern Integer     fileOk(         const File* file ); /*Last command work?*/

/* Commands: */

extern void fileFlush(           File* file );
...
extern void fileWrite64BitReals( File* file, const Real* a, Integer n );

    Usage:

      File* gridFile = fileOpen( "foo.dat", "wb" );
  
  if ( gridFile ) {
    fileWrite64BitReals( gridFile, gridCoordinates, count );

    if ( fileOk( gridFile ) ) {
      ...
    }

    fileClose( gridFile );
  }

extern VoidList* newVoidList( VoidDestroyCallback dcb, VoidCompareCallback cmp);
...

      PRE( widget );

      typedef void (Controller::* Handler)( Fl_Widget* );

      struct Entry {

        Fl_Widget* const widget; // Non-menu widget.

        Handler handler;         // Handler routine for widget.

      };

      static const Entry table[] = {

        { (Fl_Widget*) showButton,      &Controller::showHandler },

        { (Fl_Widget*) animationSlider, &Controller::animationHandler },

        { (Fl_Widget*) playStopButton,  &Controller::playStopHandler },

        { (Fl_Widget*) quitButton,      &Controller::quitHandler },

        { 0, 0 } // End of table. STEP 5: Add table entry above for new widget.

      };

      const int count = sizeof table / sizeof *table;

      int index = 0;


      for ( index = 0; index < count; ++index ) {

        const Entry& entry = table[ index ];


        if ( entry.widget == widget ) {

          Handler handler = entry.handler;

          (this->*handler)( widget );

          index = count; // Stop looping.

        }

      }


      POST( true );

    }

        playStopButton->redraw();


        while ( ! strcmp( playStopButton->label(), "&Stop" ) ) {

          const int maximum = (int) animationSlider->maximum();

          int value = (int) animationSlider->value();

          ++value;

            value = minimum;

          }


          animationSlider->value( value );

          animationSlider->do_callback( animationSlider, (void*) this );

          const int millisecondDelay = 50; // HACK: Must slow down on Linux. BUG!

          }

    Note:

    1. Header files are protected from multiple #includes by (FILE_NAME_IN_ALL_CAPS_H):

    #ifndef CONTROLLER_H
#define CONTROLLER_H
#endif /* CONTROLLER_H */

    2. C header files must contain extern "C" { to prevent name-mangling if included by C++ compilers:

    #ifdef __cplusplus
extern "C" {
#endif

#ifdef __cplusplus
}
#endif

    3. Header files have an ordered sequence of sections delineated by comments:

    
/*================================ INCLUDES =================================*/
/*================================= MACROS ==================================*/
/*================================== TYPES ==================================*/
/*================================ FUNCTIONS ================================*/
    In C++ these one-line comments are of the form: 
    //================================ INCLUDES ===================================

    Maintaining this consistent formatting is important since makedoc relies on it to automatically produce code documentation! Maintaining format consistency is easiest when new files are created from copies of existing ones.

    7. Structure definitions (contents) are not provided in the header. Instead pointers are used to dynamically allocated objects. This preserves encapsulation, minimizes the need for recompilation and facilitates inter-language object-based programming.

    /* Except for the implementation, File is just an opaque structure: */

typedef struct File File;

    8. The Command-Query Separation Principle is employed to delineate the various kinds of operations:

    /* Destructor: */
/* Constructors: */
/* Commands: */
/* Queries: */

    9. When #ifdef is used for platform-specific code inclusion, it is based on platform-standard definitions (__linux__ not some home-grown COMPLING_ON_LINUX):

    #ifdef __linux__

    10. Most platform-specific modifications are considered HACKS and are tagged as such for easier location and possible removal in the future:

          const int millisecondDelay = 50; // HACK: Must slow down on Linux. BUG!

    11. To prevent accidental name clashes, headers are included in the order from most standard to least standard: Standard C (stdlib.h), POSIX (unistd.h), Standard C++ (new), semi-standard C and C++ (FL/gl.h), external (FL/FL.H), internal (Assertions.h), local (Controller.h). The #include statements from each group are separated from the other groups by a blank line.

    12. All private (file-local) routines are declared static (thus not polluting the global namespace) and are declared fully prototyped before used.

    /*========================== FORWARD DECLARATIONS ===========================*/

static void deallocate( File* file );

static const char* typeName( const File* file );

CHECKING( static Integer isReadMode( const File* file ); )

    13. Private routines that are only used for the debug version of the library are wrapped with the CHECKING() macro.

    14. The purpose of the test program is to perform unit-level testing of the library implementation. This will be done with instrumented code (e.g., gcov, Purify and Insure++) to detect any dynamic faults in the code and to record statement coverage. The resulting reports (e.g., purify.out and insure.out) should indicate no faults and 100% statement (node) coverage. It is usually necessary to step through the code using a debugger (e.g., dbx) to force execution of failure-handling code to achieve this 100% coverage level. Other testing techniques such as branch coverage, short-tour, modal, vertex/boundary values can be applied. Efficiency testing may be done also (gprof, pixie, prof) to assess and record the statement execution profile and times.

    Sample Metrics File

    The command 'makeit metrics' causes the file 'test/metrics.out' to be generated for the source code. This is a report of various software metrics that are indicators of 'software quality'. Examples are size and complexity. This report is examined during development (after linting) and recommended changes are made to eliminate violations of 'standards'. This report is also examined during peer inspections and any remaining violations must be justifiable.

    The 'metrics' program is a UNIX C Shell script that invokes various other public-domain utilities and collects their results into a formatted report. Here is a description of the 'metrics' utility and the metrics is reports:

    metrics - Computes and reports the following software metrics
for each C and C++ source file or function:

 1. LOC - Lines Of Code (including the following classifications):
 a. Pure Code
 b. Pure Comment
 c. Both Code & Comment
 d. Blank Lines
 e. Total Code
 f. Total Comment
 g. Total Lines
 h. Pages

 2. Halstead's Metrics:

 Halstead provides various indicators of the module's complexity.
 The module is examined to determine the following:

 n1 == number of unique operators
 n2 == number of unique operands
 N1 == number of total operators
 N2 == number of total operands

 The program writes these output fields:

     File Name
     Program Length          (N  = N1 + N2)
     Program Volume          (V  = N log<base2> (n1 + n2))
     Program Level           (L  = (2/n1) * (n2/N2))
     Mental Discriminations  (E^ = V / L)

     The program volume (aka ``Halstead Volume) is probably most
     useful and seems to be reasonably well correlated with defect
     counts for modules.

  3. McCabe's Metrics:
     a. Cyclomatic Complexity - This is the number of paths through
        the function. This correlates with difficulty in testing.
        Standard value: 10
        A value of 1 means the code has no branching.
        A function's cyclomatic complexity should not exceed 10.

  4. Fan-out - The number of functions called by a given function.
        Standard value: 10
        A value of 0 means the function does not call any others.
        A function's fan-out should not exceed 10.

Usage: metrics *.[hcC]

This C-Shell program uses the following public-domain scripts and C programs:
  c_halsfilt, cyclo, fcall, halstead, lc, mcstrip, stripcom, stripstr

For assistance contact Todd Plessel, plessel.todd@epa.gov.
